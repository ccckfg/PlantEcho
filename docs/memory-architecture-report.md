# PlantEcho 记忆架构汇报

> 面向讲解的版本，重点说"为什么这么设计"和"系统是怎么记事的"，不展开具体表结构和函数实现。

---

## 一、为什么需要专门的"记忆架构"

我们做的是一个会说话的植物陪伴系统。植物要像一个真正认识你的朋友一样回应，而不是每次聊天都从零开始。这就要求系统能：

1. **记住发生过什么**——比如"上周三土壤太干了"、"主人前几天说自己在感冒"。
2. **从这些事里形成长期判断**——比如"主人最近压力比较大"、"这盆植物在干燥环境下容易缺水"。
3. **在合适的时候把相关记忆翻出来**——聊天时不是把所有历史都塞给大模型，而是找出当下真正相关的几条。

直接把所有对话和传感器数据一股脑丢给大模型有两个问题：**上下文窗口有限**、**信息越多噪声越大**。所以我们借鉴 AgentGal 项目的做法，把记忆拆成不同层次，并且让"产生记忆"和"使用记忆"是两条独立的链路。

---

## 二、记忆的分层：人类是怎么记事的，系统就怎么记

我们把植物的"记忆"按稳定程度分成五层，越靠下越稳定、越接近人格的一部分：

| 层次 | 类比人类 | 系统中的角色 |
| --- | --- | --- |
| **稳定个性** | 一个人的性格、说话习惯 | 每株植物绑定的角色画像，决定语气和偏好 |
| **当前状态** | 现在的心情、最近在关注什么 | 植物当前心情、关系亲密度、最近摘要 |
| **近期对话** | 短期记忆，刚刚说过的话 | 最近若干轮聊天原文 |
| **情节记忆** | "上周三发生了什么" | 重要事件被整理成的一条条故事 |
| **稳定理解** | 长期形成的判断："主人是个夜猫子" | 从多个事件里提炼出的长期认知 |

**关键点**：上面四层相对短期、变化快；最下面两层是长期沉淀。这种分层让系统能在不同时间尺度上"用对的信息"。

## 三、记忆是怎么生成的：从"发生过的事"到"被记住的事"

这是整个架构里最核心、也最容易被误解的部分。**不是所有数据都会变成记忆**——传感器每分钟都在上报，如果全记下来等于没记。我们只把"值得记的事"沉淀成长期记忆。

### 什么算"值得记"

- 土壤湿度低于或高于养护阈值（缺水、积水）
- 光照、温度等出现需要注意的异常
- 主人主动告诉植物自己的状态、情绪或重要日常

普通的、平稳的传感器读数只进原始数据表，不进入记忆。

### 生成流程：草稿 → 后台整理 → 长期记忆

```text
事件发生 → 写一份"草稿" → 后台任务把草稿整理成"故事" → 故事再升级成"长期理解"
```

具体五步走：

1. **打草稿**
   每次用户消息或重要传感器异常，先写入一个"记忆草稿"。这一步很轻量，不影响聊天回复速度。

2. **调度后台任务**
   一轮对话结束后，调度一个后台整理任务。**整理是异步的**——用户聊天该多快还是多快，不会等记忆整理完才回话。

3. **检测"事件闭合"**
   一段对话什么时候算"结束"了？由大模型来判断："话题是不是变了？这一段事情是不是说完了？"只有闭合的片段才会被整理成记忆。这避免了把还没说完的话过早归档。
   *领域扩展*：传感器异常是天然闭合事件（比如缺水触发了一次警报，事件本身就有头有尾），会直接进入整理流程。

4. **生成情节记忆**
   闭合的对话片段交给大模型，提炼出一条结构化的"情节记忆"：发生时间、关键词、重要度、标题、内容。**原始对话也会被保留**，作为可追溯的来源，但不参与后续的检索匹配，避免噪声。

5. **更新稳定理解**
   新的情节记忆产生后，再让大模型判断："这件事有没有改变我对主人的长期认知？"如果有，就在稳定理解里新增一条或更新一条。这是从"事件"到"判断"的升华。

### 一个让系统不丢记忆的设计

整理是会失败的——大模型可能超时、可能返回格式错误。所以系统的规则是：

- **草稿只有整理成功后才标记为已消费**，失败的草稿会留着，下一轮重试。
- 整理任务本身也是持久化的，进程重启不会丢；同一份事件不会被重复整理（去重）；卡住的任务会自动恢复。
- 如果新一轮对话进来时，上一轮的整理还没跑完，新的轮次会被记下来"待处理"，等当前任务结束后再补跑。

**核心思想**：宁可多跑几次，也不能让记忆漏掉。

### 没有大模型时怎么办

如果还没接入大模型，普通对话型的记忆暂时不会生成（因为需要语言理解能力来做闭合判断和故事生成）。但**传感器异常类的记忆有一个本地兜底**——因为它们结构化、闭合明确，系统可以用规则直接生成一条情节记忆。这保证了硬件链路在任何情况下都能产出记忆。

## 四、记忆是怎么被找回来的：聊天时如何"想起相关的事"

光记下来没用，关键是聊天时能把对的记忆翻出来。这一步叫"召回"，也是 RAG 的核心。

### 一个直觉：人怎么回忆？

人在听到一句话时，会**同时**用两种方式回忆：
- **意思相近**："这句话让我想起什么类似的场景？"
- **关键词相同**："这里面提到的东西，我记得我之前说过。"

我们的系统也是这两条路并用。

### 召回流程

```text
1. 把当前情境组成查询（最近对话 + 传感器场景 + 当前关注点 + 主人新消息）
2. 走两条路找候选：
   ① 语义相似（向量检索）
   ② 关键词命中（全文检索 BM25）
3. 把两路结果融合（向量权重 0.75 + 关键词权重 0.25）
4. 可选：再过一轮"重排"模型做精排
5. 综合"相关度 + 多近 + 多重要"决定最终顺序
6. 记录"这条记忆被想起来过"，下次更倾向于优先想起
```

最终排序公式可以理解成一句话：**"这条记忆有多相关，叠加它有多新、有多重要"**。

```text
final = 相关度 × 0.50 + 新近度 × 0.20 + 重要度 × 0.30
```

新近度用指数衰减——越久远的事，权重衰减得越快，但不会归零。重要度来自记忆生成时大模型给出的评分。

### 情节记忆和稳定理解走不同的查询

情节记忆查的是"具体发生过什么"，所以查询里会带传感器场景；稳定理解查的是"对主人/植物的长期判断"，所以查询里会带关系摘要。两者并行召回，给聊天提供互补的上下文。

### 没有向量模型也能用

如果还没配 embedding 模型，系统只走关键词检索这一路也能工作，只是质量会下降。配上 embedding 后会自动建立向量索引，召回质量提升。

## 五、整体数据流：把上面三段串起来看

```text
┌─────────────┐       ┌───────────────┐       ┌─────────────────┐
│ 传感器异常   │──────▶│  记忆草稿      │──────▶│ 后台整理任务     │
│ 用户消息    │       │ (memory_drafts)│       │ (background_jobs)│
└─────────────┘       └───────────────┘       └────────┬────────┘
                                                       │
                                                       ▼
                                              ┌─────────────────┐
                                              │  闭合检测        │
                                              │  情节记忆生成    │
                                              │  长期理解更新    │
                                              └────────┬────────┘
                                                       │
              ┌────────────────────────────────────────┤
              ▼                                        ▼
       ┌─────────────┐                        ┌─────────────────┐
       │ 情节记忆     │                        │ 稳定理解         │
       │             │                        │                 │
       └──────┬──────┘                        └────────┬────────┘
              │                                        │
              └─────────────┬──────────────────────────┘
                            ▼
                   ┌─────────────────┐
                   │  混合召回        │  ◀── 聊天时
                   │ (向量 + 关键词)  │
                   └────────┬────────┘
                            ▼
                   ┌─────────────────┐
                   │ 重排 + 综合排序 │
                   └────────┬────────┘
                            ▼
                       带记忆的回复
```

写入和读取是**两条解耦的链路**——写入慢一点没关系（异步），读取必须快。

## 六、这个架构解决了哪些实际问题

| 问题 | 解决方式 |
| --- | --- |
| 上下文窗口有限，不能把所有历史塞给模型 | 分层 + 召回，只把相关的几条塞进去 |
| 聊天响应不能因为整理记忆而变慢 | 整理放到后台任务，写入读取解耦 |
| 大模型偶尔会失败，会不会丢记忆？ | 草稿持久化，整理失败保留草稿，下次重试 |
| 怎么避免相同的事被重复记录？ | 后台任务去重，闭合检测控制粒度 |
| 没有大模型时系统能不能工作？ | 传感器事件本地兜底，关键词检索也能召回 |
| 怎么避免老记忆永远占据视野？ | 新近度衰减，但保留重要度作为反向力量 |
| 怎么知道"这条记忆是被翻出来过的"？ | 召回时更新最后被想起的时间 |

## 七、一句话总结

这套记忆系统做的事，本质上是**让一个程序具备类似人类的"分层记忆 + 选择性记忆 + 联想式回忆"**：

- **分层**：从"刚说过的话"到"对主人的长期认知"，五个层次各有职责。
- **选择性**：不是所有事都记，只记值得记的；不是所有草稿都立刻生效，要等事件闭合。
- **联想式**：聊天时不靠死记硬背，而是同时用"语义相似"和"关键词命中"两条路找出相关的几条。

这样植物才不只是一个会响应的接口，而像一个慢慢认识你的伙伴。
